# Agent entry path and measured recipes

Start with `capabilities`, then `doctor_target` for the explicitly selected build,
provider and backend. Read the returned capability/restriction fields. After
attach, query `session_capabilities`; the server catalog alone does not prove a
live application's support. Prefer stable names/automation ids and title-based
window aliases. Inspect before acting, declare the expected postcondition, and
wait for that condition. A dispatched input is not proof that a task succeeded.

The executable examples are [agent-recipes.json](agent-recipes.json). They target
the small application generated by `eng/test-integration-onboarding.ps1`, whose
two windows deliberately complete an action asynchronously. Bind `${...}` values
from the current run. These fixture names are not selectors for another app.
The conformance runner checks every example against the running MCP server's
actual JSON schema before dispatch, and executes both CLI and MCP variants.

## Connect any stdio MCP client

Use this server entry inside the client's own server-configuration wrapper:

```json
{
  "command": "dotnet",
  "args": ["/absolute/path/to/AvaScope.Mcp.dll"]
}
```

On Windows, the assembly path can be `C:/Tools/AvaScope/AvaScope.Mcp.dll`.
For an installed CLI, the equivalent entry is `command: "avascope"` and
`args: ["mcp"]`. Use an absolute command path when that client has a different
PATH. Do not start a TCP server. The recipe runner performs a real stdio
handshake and writes the tested `mcp-server.json` entry next to its results.

Keep the app's environment separate from the MCP client's configuration. Use
[test profiles](AGENT_TEST_PROFILES.md) for explicit build/launch arguments,
backend choices and environment references. Reference secrets by environment
variable name; keep their values out of committed configuration and prompts.
Restart the MCP server after changing its own environment.

## Fresh project to first verified inspection

1. Run `integration_guide` with the exact project path. Apply the returned edits
   to the actual startup location. The host must explicitly choose activation
   behind its diagnostics/test flag. Review unresolved startup diagnostics.
2. Build with that flag. For an external provider, use `verify_provider` with its
   explicit directory and pins, then [verify integration](STANDALONE_PROVIDER.md)
   through `verify_integration`. Test enabled and disabled outputs; the disabled
   build must produce no AvaScope session or listener.
3. Resolve the chosen profile, then `run_scenario` with the profile file/name.
   Check launch, readiness, workflow and cleanup outcomes separately. The
   generated clean-project gate exercises both package and standalone modes,
   enabled/disabled builds and a declared safe input target through CLI and MCP.
4. For an app kept open by an owned scenario, use its returned **sessionId** in
   `attach_to_app`, query its capabilities, and call `observe` with an explicit
   title/id scope and bounded `maxNodes`. Preserve the returned screenshot and
   evidence paths. Never choose an unrelated process using `latest=true`.

CLI counterparts are listed with each executable recipe. For example:

```sh
avascope integration-guide --project /absolute/App.csproj
avascope verify-provider --directory /absolute/provider
avascope resolve-test-profile --profile-file /absolute/profiles.json --profile inspect
avascope run-scenario --profile-file /absolute/profiles.json --profile inspect
avascope attach --session <returned-session> --manifest-dir /explicit/manifests
avascope session-capabilities --session <returned-session> --manifest-dir /explicit/manifests
avascope observe --request observation.json --manifest-dir /explicit/manifests
```

## Multiple windows and failure evidence

Use the `multi-window` example as the `request` for `run_workflow`. It invokes
`OpenDetails` in the main window, verifies the new window's title, invokes
`Complete` there, and waits for `Outcome.Text == Ready`. The definition uses no
stored node ids, coordinates or sleeps. Its MCP schema requires `topLevelId`
even with aliases, so the example explicitly sets it to `null`.

For a new regression, retain the expected `Ready` condition. Do not replace it
with an observed wrong value to make the run pass. Inspect the failed step's
verification, inspection/tree/screenshot evidence and report pack. Preserve
JSON, Markdown and JUnit reports with the original redaction policy. Use
[workflow export](WORKFLOW_EXPORT.md) after an executed supported workflow if a
parameterized regression definition is useful.

Classify failures from evidence:

| Observation | Decision |
| --- | --- |
| Missing executable/dependency/display, incompatible provider, failed activation or control ownership | Environment/integration problem; fix the reported prerequisite before UI actions. |
| App is attached, the intended action ran, and its original postcondition observes the wrong application state | Application or test-expectation failure; inspect the recorded state before attributing a product defect. |
| Selector is ambiguous, target is stale, condition is unsupported, or evidence is incomplete | Unresolved; refine the target or obtain the missing evidence. Do not invent an application diagnosis. |

The application seed in this fixture explicitly returns `Broken` after an
otherwise valid action. The environment seed points launch at a nonexistent
executable. This known ground truth permits scoring these cases; it is not a
general rule that every failed workflow implies a product bug.

When finished, terminate only the owned run through `recover_run` with its
returned run id and `operation: "cleanup"`, or request termination in the
scenario itself. Keep evidence. Attached applications remain outside owned
process cleanup. See [run recovery](RUN_RECOVERY.md).

## Reproducible conformance

From a repository checkout with .NET 10 and PowerShell 7.4+:

```powershell
./eng/test-agent-recipes.ps1
# Same public surfaces on the current native Windows/macOS desktop:
./eng/test-agent-recipes.ps1 -Native
```

On Linux X11, supply a working explicit display, or run a private display for
this test's lifetime:

```sh
xvfb-run -a -s "-screen 0 1280x900x24 -nolisten tcp" \
  pwsh -NoProfile -File eng/test-agent-recipes.ps1 -Native
```

Install the X11/runtime dependencies described in [target readiness](TARGET_READINESS.md).
`-Native` selects X11 on Linux, Win32 on Windows and AppKit on macOS. The default
uses Headless and records that provenance. Native permission-limited operations
and macOS remote picker confirmation remain subject to the
[input support matrix](INPUT_STRATEGIES.md); these recipes do not claim to test
unsupported actions. A working X11 recipe is not Wayland-native coverage.

`-RepeatCount` accepts 2–4. `-Surfaces Cli` or `-Surfaces Mcp` narrows the adapter.
`-SkipBuild` requires a current solution build **and a freshly packaged provider**;
same development version numbers do not prove that local binaries match.
`-OnboardingReport` can reuse a successful report produced on the same backend
by the current generated fixture, avoiding repeated package/publish work.
`-SchemaOnly` checks all examples through the real stdio tool catalog without
building/launching an app. Schema checks use PowerShell's
[Test-Json](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/test-json).

`artifacts/agent-evaluations/<id>/evaluation.json` records the server version,
platform/backend, recipe SHA-256, repetitions, task completion, failure
classification, actual public tool-call counts and per-call timings. A workflow
counts as one public call; its internal steps are not separate agent calls.
Builds and MCP initialization/schema discovery are setup, not tool calls.
CLI timings include process startup. MCP recipes share one live connection for
their session; closing a probe between actions can terminate the server's owned
process tree. Do not use a sequence of one-shot MCP probes to test a persistent app.
Successful onboarding is measured separately, including its actual calls.
Reports and redacted tool outputs are retained; transient request binding files
are removed. Independent repetitions are not retries. The fixed script performs
no automatic retry, so its unnecessary retry count is zero.

These results are labeled `deterministic_conformance`, with `model: null` and
`agentOutcomesMeasured: false`. They establish recipe correctness, not a model's
ability to choose the right next action.

## Agent-directed trials

Give the agent the generated project's path, its explicit provider/profile,
and one task: establish inspection on a fresh build, complete the two-window
flow, or diagnose why it cannot complete. Reset application state between
trials and keep the original condition. Use the same recipe revision/backend,
tool budget and seed schedule when comparing clients/models. Preserve any
failed trials instead of silently rerunning until success.

The repository MCP probe can record **actual agent-chosen** calls while retaining
normal request/response behavior. Set these variables on the probe process:

```powershell
$env:AVASCOPE_AGENT_TRACE_FILE = '/private/trial/tool-events.jsonl'
$env:AVASCOPE_AGENT_TRIAL_ID = 'application-1'
$env:AVASCOPE_AGENT_CONTEXT = 'initial'
$env:AVASCOPE_AGENT_RETRY = 'none'
dotnet tests/AvaScope.McpScenarioClient/bin/Release/net10.0/AvaScope.McpScenarioClient.dll `
  /absolute/AvaScope.Mcp.dll /private/request.json /explicit/manifests run_workflow
```

For a sequence against an app launched by that server, keep the probe alive:
replace the final tool name with `--stdio-session` and send one JSON line per
command, `{"tool":"health","arguments":{},"measurement":{"trialId":"clean-1","contextRevision":"initial","retryDisposition":"none"}}`.
Each line returns one structured result. Use the usual tool argument objects;
the optional `measurement` overrides the per-trial environment labels. The
probe accepts at most 128 calls over ten minutes. Close standard input after
owned run cleanup to finish. This is evaluation infrastructure, not a new
public AvaScope transport or foreign workflow language.

Trace records contain tool name, request fingerprint, result status/stage,
transport completion, duration and server version. They contain no argument or
response text. `AVASCOPE_AGENT_RETRY` is `none`, `necessary`, `unnecessary` or
`unknown`; update context after obtaining new evidence or fixing the environment.
An unexplained identical call in unchanged context remains unknown. Annotation
is an evaluator judgment, not an automatically proven model property. A trace
write failure after dispatch must not trigger another application action.

Other clients can emit the same small AvaScope evaluation event contract from
their actual tool-call logs. This measures tool use; it does not import or run a
foreign test framework or interpret its workflows. The measured trace must not
be generated by relabeling the conformance script's events.

Supply an outcomes document:

```json
{
  "schemaVersion": 1,
  "mode": "agent_outcomes",
  "client": "actual client and version, or explicitly unreported",
  "model": "actual configured model, or unreported",
  "configuration": { "backend": "headless", "toolBudget": 20, "recipeSha256": "recorded hash" },
  "trials": [
    {
      "trialId": "application-1",
      "expectedClassification": "application",
      "reportedClassification": "application",
      "taskCompleted": true,
      "evidencePaths": ["/private/trial/workflow-report.json"]
    }
  ]
}
```

```powershell
./eng/measure-agent-evaluation.ps1 -TracePath /private/trial/tool-events.jsonl `
  -OutcomesPath /private/trial/outcomes.json -OutputPath /private/trial/measured.json
```

The report keeps actual call counts, explicit completion/classification decisions,
unknown retry judgments, transport failures, evidence hashes and client/model/
configuration provenance. It rejects conformance traces and missing trials or
evidence. Completion and seeded ground truth are declared by the evaluator;
they are not cryptographically attested. A few repeated trials demonstrate a
reproducible measurement path, not a statistically reliable model ranking.
